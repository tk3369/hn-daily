    Nitter refuses X's takedown demand and lives on

    On 24 August 2026 X Corp sent cease-and-desist letters demanding the permanent takedown of Nitter instances and the project's repository. Following legal advice, the README now states the Nitter project will continue. The privacy-first alternative Twitter frontend survives — and XCancel is back too.

    • What happened
      • X Corp demanded a permanent takedown of both the Nitter repo and independent Nitter instances.
      • Two weeks later, a single README commit — “Nitter lives” — says legal advice backs continued operation.
    • Why it matters
      • Crucial public-service information (Paris metro outage feeds) is posted only to X; alt frontends are infrastructure, not nostalgia.
      • A legal win here sets the template for every scraping-alternative under platform pressure.
    • HN take
      • Relief mixed with an awkward question: do alt frontends just prolong X's life by making it usable without an account?
      • The "agent-first API" hope gets mocked — platforms need no APIs to drown in botspam.

    What HN commenters are sayingRelief dominates, but the most interesting tension is whether Nitter helps or harms: without it, commenters argue, users would get fed up with X faster and move on — alt frontends may only extend the platform's life. The strongest case for Nitter is infrastructural, not nostalgic: Paris transit outages are reliably posted only to X accounts, so the frontend is how non-users get critical information.     • Why it matters

    A Python interpreter that fits in 1024 bytes

    Austin Henley's 1024-byte Python interpreter is exactly as nasty as it sounds: any “f” is `for x in range(y)`, any “w” is `while`, any “p” is `print(`. No error checking, no mercy — just the minimal code to run one specific demo.

    • The trick
      • Keyword detection by first letter only: f=loop, w=while, i=if, d=def, p=print — so `w = 4` is a syntax death.
      • Every shortcut Sector C wouldn't take: the interpreter assumes its input is already correct.
    • The lineage
      • C4: tiny but complete C with real error checking. Sector C: shortcuts. This: nastier than both.
      • Technique overlap with JavaScript minification and Apple II BASIC's two-letter variables.
    • HN take
      • Delight at the nastiness plus practical notes — dicts via linear lookup save code if you give up performance.
      • Kolmogorov-complexity jokes land: this is TDD taken to its absolute limit.
    Source: austinhenley.com · Discuss: HN Discuss · 265 pts / 96 comments

    What HN commenters are sayingDelight and gentle horror in equal measure. The thread's joy is in naming the nastiness: first-letter keyword dispatch means `w = 4` can't exist, and the code only makes sense with the article as its decoder ring — the GitHub “readable” version has fewer comments than the post. Comparisons place it on the spectrum: C4 was tiny but complete with error checking, Sector C took every shortcut and assumed correctness, this goes further and assumes the script itself. Practical wisdom sneaks in — linear-lookup dicts for tiny interpreters, the insertion-order guarantee of Python dicts — and the historical rhymes: JS minification tricks, Apple II BASIC's two-letter variable names (luxury versus one-letter interpreters). The Kolmogorov-complexity framing wins: the simplest program that passes the test.

    Ask HN: how do you actually manage all these skills files?

    With AI coding agents hungry for “skills” files, someone asks the obvious: how is anyone managing this pile? The thread splits between “skills are snake oil” and “they're just macros that save tokens” — and both sides have a point.

    • The skeptic case
      • With good repos and good prompts, agents find what they need — skills are downloaded kung fu for a problem that's mostly gone.
      • Needing to manage them at all is a code smell; the useful ones are team-shared repo macros.
    • The practitioner case
      • It's not about discovery — it's about not re-spending tokens re-learning the same how.
      • Anthropic's rule: less in context, more in skills; keep the how out of context until invoked.
    • HN take
      • Consensus forms around curation: adapt skills per project, don't blindly accumulate; too many skills bloat context even unread.
      • Proprietary tech not in training data is the killer use case.
    Source: news.ycombinator.com · Discuss: HN Discuss · 191 pts / 176 comments

    What HN commenters are sayingThe thread converges on a synthesis rather than a winner: skills are most defensible as repo-local macros that encode process — the how, kept out of context until needed, as Anthropic's guidance has it — and least defensible as downloaded kung-fu downloaded from the internet. The skeptics' strongest point stands unrebutted: if you have so many skills they need managing, that's a code smell, and unread skills still cost context. The practitioners' strongest point stands too: token savings are real and measurable for repeated tasks, and agents can't infer what isn't in training data — proprietary stacks make skills mandatory. The resolution everyone lands on: curate per project, adapt, don't accumulate.
