    AI cracks a 370-year-old cipher — maybe

    Fable 5.1 decoded the Cyphral Distich, a 1652 cipher by Thomas Urquhart, via a book cipher into his Logopandecteision: 44 minutes, ~176k tokens, zero interjections. The same rule nearly decoded the larger Cyphral Octastich. But HN is fighting over verification: a 2014 German blog comment already proposed the book-cipher approach, nobody can find the cipher on Klaus Schmeh's Top-50 list, and the author admits full physical replication is still pending.

    • What shipped
      • Book cipher: 32 numbers per line index the i-th Proquiritation in Urquhart's Logopandecteision (1653); word indices yield first letters spelling "O GOD UPHOLD KING CHARLS THE SECOND AND MAKE HIM THE SUPREME RULER OF THIS LAND".
      • The author reports ~44 minutes and ~176k tokens with zero interjections; the same rule decoded the 285-number Cyphral Octastich (1652) all but nine letters, checked against EEBO-TCP text with stated caveats.
      • Second camp argues the real feat was problem selection — the model picked a tractable unsolved problem.
    • The catch
      • A 2014 German-language blog already had commenters proposing the book-cipher approach ("the solution should be findable with the help of the book").
      • The cipher doesn't appear in Klaus Schmeh's Top-50 list of encrypted books, and commenters couldn't find it in archive.org copies of Urquhart's works — "hallucination" doubts.
      • The article itself admits full physical replication of the larger cipher is pending and asks readers for a 1983 edition or physical copy.
    • Why it matters
      • Even skeptics concede the capability: agentic LLMs clearing long-tail problems bottlenecked on human attention. That persistence is the story.
      • Selection bias caveat: aim a model at every unsolved cipher and showcase the one it cracks. Treat this as "unverified solve with stated caveats," not a closed case.

    Julia 1.13 goes after its oldest complaint: latency

    Iterative polish release aimed squarely at latency: ~20% faster startup, ~30% faster precompile than 1.12, and the GC now skips permanently-marked image objects (GC.gc() from 35ms to 2ms bare). Warm but clear-eyed reception — most new features got pushed to 1.14. Watch out: the hash function changed, and Pkg now defaults to zstd — check hash-dependent tests before upgrading.

    • The numbers
      • Startup ~20% faster (hyperfine: 69.1ms → 56.7ms); precompile ~30% faster than 1.12 (~10–20% vs 1.10 LTS), per the release blog.
      • GC change: sysimage/package-image objects load permanently marked; the mark phase never enters them — full-collection cost now scales with the program's own heap, not loaded code size (GC.gc(): 35ms → 2ms bare, 187ms → 68ms with GLMakie on M4 Pro).
      • TTFX CI tracking is now built into Julia's own development process since Sep 7, 2026.
    • Other wins
      • REPL upgrades: built-in syntax highlighting, fzf-style history search; reliable Ctrl-C again.
      • Hash function replaced with RapidhashNano (C → pure Julia, streaming); Pkg asks for zstd-compressed archives instead of gzip by default; new @__FUNCTION__ macro and --trace-eval flag.
    • Production note
      • Hash seed/values changed — any serialized hashes or hash-dependent tests will break across 1.12 → 1.13.
      • Grievances: packaging still tied to GitHub, a Pluto-vs-Bonito notebook schism, loose interface definitions, sparse learning resources vs. Python, and one disputed thread arguing ergonomics is losing priority to agent-driven development.
    Source: julialang.org · Discuss: HN Discuss · 257 pts / 40 comments

    What HN commenters are sayingReception is warm but clear-eyed: this is an iterative polish release — most new features got pushed to 1.14 — focused on latency, the GC, the REPL, and interrupts. Startup time, Julia's longest-running complaint, is directly addressed: ~20% faster startup, ~30% faster precompile than 1.12, and the GC now skips permanently-marked image objects. Commenters also like the REPL upgrades (built-in syntax highlighting, fzf-style history search), the RapidhashNano hashing swap, reliable Ctrl-C again, Pkg defaulting to zstd, and TTFX CI tracking now built into Julia's own development process.     The case against JPEG XL — on the web, at least

    A codec engineer (computerbuster, SVT-AV1 perceptual tuning) argues modern AVIF encoders now beat JXL on lossy efficiency across the fidelity range, JXL is weak on non-photographic images, and decode is slow — including a 2KB "prime image" that took 17.43s of user time to decode on an M5 Pro (one commenter reproduced a DoS on macOS QuickLook: all cores, 4GB RAM, 15s). The author showed up for an AMA. Pushback: JXL's pitch is versatility — lossless JPEG recompression, DNG 1.7 raw, PDF embedding — not just the web.

    • The numbers
      • jxl-rs decodes a 5456x3632 image in ~1209ms single-thread; a crafted 1,918-byte prime image took 17.43s user time to decode; lossless JXL ~11.9% smaller than lossless WebP on the author's dataset.
      • Chrome rejected JPEG XL in 2023; a new Rust decoder (jxl-rs) entering Chrome/Firefox "in some capacity" may be shifting the memory-safety objection and browser stances.
      • JXL is in the DNG 1.7 spec (lossless raw compression) — recent iPhones and Samsung Android phones already ship JXL codecs for this; Safari supports JXL but not progressive decode.
    • The rebuttals
      • The single-thread decode benchmark is misleading — a JXL dev cites 240–270 MP/s on 6 cores with the C++ decoder.
      • Browsers won't regress 4:4:4 AVIF support, so the 4:2:0 hardware-decode fear is overblown; the progressive-AVIF comparison cherry-picks the one point where AVIF looks better.
    • Production note
      • If you accept JXL uploads, the prime-image DoS demo means decode-time limits matter — don't let users hand you arbitrary JXL and decode it synchronously.
      • Consensus split: "right about the web, wrong to dismiss it entirely" — JXL as universal archive format has a real constituency (scientific imaging to web photos, up to 4096 channels).
    Source: giannirosato.com · Discuss: HN Discuss · 219 pts / 281 comments

    What HN commenters are sayingThe author (computerbuster, a codec engineer behind SVT-AV1 perceptual tuning and Iris-WebP) showed up for an AMA, which anchors a surprisingly technical debate. The article's core claims: modern AVIF encoders now beat JXL on lossy efficiency across the fidelity range, JXL is weak on non-photographic images (no directional prediction, no deblocking filter, awkward patch/intra-BC machinery), and decode is slow — 1209ms single-thread for a 5456x3632 image on jxl-rs, plus a 2KB "prime image" that takes 17.43s of user time to decode on an M5 Pro (one commenter reproduced a DoS on macOS QuickLook: all cores, 4GB RAM, 15s from a 2KB file — Apple's JXL previewer lacks sane limits). The pushback is organized: JXL's real pitch is versatility, not just the web — lossless JPEG recompression (~20% smaller, reversible byte-for-byte), DNG 1.7 support, PDF embedding, up to 4096 channels, one format spanning scientific imaging to web photos. Specific rebuttals: the single-thread benchmark is misleading; browsers won't regress 4:4:4 AVIF support; the progressive-AVIF comparison cherry-picks. Consensus split: "right about the web, wrong to dismiss it entirely."
