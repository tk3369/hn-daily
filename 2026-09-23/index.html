    How did AMD Ryzen get 50% faster in two years? Wider cores, not faster clocks

    Daniel Lemire compares Ryzen 7 5800X3D (Zen 3, 2022) → 9800X3D (Zen 5, 2024): +47% single-core, +58% multi-core on Geekbench 6. Clocks contributed only 15% (4.5→5.2 GHz). The rest came from transistors up ~50% (11B→16B), almost all in the core: dispatch width 6→8, integer ALUs 4→6, reorder buffer 256→448, L2 512KB→1MB per core, L1D 32KB→48KB — and Zen 5 as the first full-AVX512 desktop core (four 512-bit SIMD units, two 512-bit loads/cycle). Conclusion: CPUs get wider, not faster. Next: Zen 6 and a 256-core Epyc 'Venice' with 1GB of L3.

    • The numbers
      • 5800X3D→9800X3D single-core: 2,016→2,969; multi-core: 11,832→18,751
      • Max boost only rose 15%; transistor count rose ~50%, mostly in the core
      • Zen 5: first desktop core with real 512-bit SIMD — 'normal compiler devs' finally have it
    • HN take

    Microsoft killed FoxPro in 2007. Anyway, here's FoxPro revived — FoxDev Studio rebuilds it 64-bit

    Microsoft killed FoxPro in 2007. FoxDev Studio is the resurrection: opens your existing projects, forms, class libraries, menus, reports, and .dbf tables in place — no migration step. 64-bit throughout, so the 2GB table ceiling (signed 32-bit offsets in file handling) is gone; the same files run into the hundreds of GB — a one-way door, since >2GB tables won't reopen in VFP. The VM is written in Rust, compiled to WebAssembly; behavior is settled by asking Visual FoxPro 9 itself (1,534 of 1,722 language-reference elements test-verified against it). Adds FoxScript: lambdas plus HTTP routing. Old 32-bit .fll libraries load through a helper process. Nightlies on GitHub, unsigned.

    • The build
      • Compiler + bytecode VM in Rust→Wasm; editor lints through the actual runtime compiler
      • 32-bit bridge: SET LIBRARY TO spawns a helper process for old .fll files; DECLARE ... DLL reaches modern libraries in-process
      • Fiber-based VM: MESSAGEBOX() stops your program without freezing the window, like FoxPro always did

    Jev in 25 lines of Python: logprob classification without the hype

    NobodyWho parodies the Jev hype — 'Everyone and their mom is talking about Jev' — by reimplementing the core in 25 lines: load a 0.6B Qwen GGUF locally via llama-cpp, present a multiple-choice email prompt (Legitimate / Spam / Phishing), read the logits for the label tokens, softmax into probabilities. No API, no synthetic data, no RL. The real Jev (typesafe.ai) trains models with RLCD — Reinforcement Learning for Calibrated Decisions — for calibrated probabilities, which raw logprobs are not. The post is a parody; it links OpenJev implementations for the serious version.

    • The trick
      • tokenize the labels, grab their logits, logaddexp-softmax → probabilities
      • Qwen3-0.6B-Q8_0.gguf classifies the test email 'Phishing' at 0.885
      • Fast, local, no data leaves the machine — the point NobodyWho actually cares about
    • HN take
      • Pulling logprobs from chat models is 'icky' — chat models are trained to write prose; use structured outputs instead
      • Calibration check: the choice tokens must sum to ≥95% of the distribution or the model isn't following instructions
      • LLMs show position bias toward 'A' — disputed whether it's real bias or prose-training leakage
    Source: nobodywho.ai · Discuss: HN Discuss · 368 pts / 122 comments

    What HN commenters are sayingThe thread is a practitioner-level argument about calibration. The top comment is unimpressed by the logprob trick: going directly for logprobs with a chat model is 'icky' because chat models are trained to write prose, so your choice tokens get diluted in whatever else it wanted to say — structured outputs solve it better. The counter-experience: 'The whole point is the quantified output. If you just ask an LLM to type out its confidence manually, it'll make up some nonsense. A dry undercurrent: if you want calibrated probabilities, you train for them — that's what the real Jev does.

    SAML: a fractal of bad design — retire it for OIDC

    Trail of Bits argues SAML should be deprecated: born 2002 from a committee of subcommittees that jammed four XML security protocols into one, built on XML's bug classes (XXE, billion laughs, canonicalization), with signature-wrapping attacks known since 2012 and still present in 2025 (GitHub Enterprise, PortSwigger). 99% of implementations use ~10% of the kitchen-sink spec; it ossified before mobile, SPAs, and IoT existed. Ptacek, quoted: it works 'if you assume XML signature validation is reliable. But XML signature validation is deeply cursed.' The migration path: OpenID Connect.

    • The five fatal flaws
      • Built on XML: tags, namespaces, CDATA, DOCTYPEs vs JSON's keys/values/objects/lists
      • Canonicalization + enveloped signatures: signing data you're simultaneously modifying
      • Kitchen-sink design, ossification: transport-independent assumptions from the VPN era
    • HN take
      • War stories: xmlsec verifying signatures against an HMAC key from the attacker-controlled document
      • The classic bug: verify the signature, then trust the whole document instead of the signed part
      • 'Probably the worst security specification ever written' — plus the Hoare quote on simplicity
    Source: blog.trailofbits.com · Discuss: HN Discuss · 289 pts / 151 comments

    What HN commenters are sayingThe thread is a support group for SAML survivors. The favorite horror story: a mainstream xmlsig implementation that would check the signature 'against an hmac using a password specified in the attacker controlled document' — or against Web PKI, so an attacker could sign with their own domain's TLS key and be accepted. 'I honestly don't know how sites with saml aren't getting hacked all the time.' The signature-wrapping classics get retold: implementations that verify a signature and then 'just trusted the document as a whole rather than only the part that was signed.' Nobody defends the spec — 'It really probably is the worst security specification ever written,' 'three entire specs bundled as one' — but there's one fair defense: XML was what existed in 2001-2002; JSON was experimental. The Hoare quote lands the verdict: 'make it so simple that there are obviously no deficiencies' beats 'so complicated that there are no obvious deficiencies.'
