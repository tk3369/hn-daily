    Pi hits 1.0: the minimal agent harness hardens up

    Earendil shipped Pi 1.0, the hardened release of its minimal, extensible agent harness used by hundreds of thousands weekly. New in 1.0: Codemode with native MCP and non-LLM model support (Jev, image models), virtual-model extensions, deferred tool loading, Anthropic cache warming, mid-conversation system messages, a new TUI theme, and full-screen by default. The pitch is restraint: adopt only what has proven itself, weigh every feature against its complexity.

    What HN commenters are sayingCelebration first — 'Finally a government doing something that benefits us' — then the thread settles into OpenStreetMap's licensing knot. The claim: OSM can't ingest data whose license requires direct downstream attribution, because OSM attributes contributors collectively via its Contributor pages, which is either principled hygiene or, as one commenter puts it, hypocrisy — OSM demands its own attribution while rejecting sources that demand theirs.     Cloudflare's Clef tops the decision-model index, open weights

    Git 3.0's SHA-256 default will be a costly mistake

    GitButler's Scott Chacon argues Git 3.0's plan to default new repos to SHA-256 is a global train wreck for near-zero benefit. SHA-1 collisions (SHAttered 2017, Shambles 2020) are manufacturable but second-preimage attacks remain infeasible — even MD5 preimage would take ~16 billion years on every GPU on Earth. Trust in Git was never the hash, Linus said in 2005: 'the real security is in distribution.' The cost: a split ecosystem where every repo, forge, and user must know which hash bucket they're in.

    • The argument
      • SHA-1 'broken' = collisions manufacturable, not preimage attacks
      • Even MD5 preimage: ~16B years on 3B RTX-5090s — effectively immune
      • Linus (2005): security is in distribution, not the hash
    • The cost
      • git init defaults split the world into SHA-1 and SHA-256 buckets
      • Forges must ask which format; repos can't mix; tooling doubles
      • Google's migration prep (Emily Shaffer's talk) is 'not a pretty picture'
    • HN take
      • Top comment: 'full of mistakes' — SHAttered was practical, collisions suffice
      • 'Impractical' for whom? Nation-states spent 5 years on Stuxnet
      • Optional migration = no migration (the PKI postquantum analogy)
    Source: blog.gitbutler.com · Discuss: HN Discuss · 466 pts / 429 comments

    What HN commenters are sayingThe top comment calls the post full of mistakes, and the thread litigates from there. The corrections: SHAttered was a practical proof of concept, not theory, and collision attacks do matter — two checkouts can verify against the same commit hash yet contain different code, which is exactly a code-smuggling shape. Chacon replies in-thread that he links both papers, calls exploitation impractical rather than impossible, and stands on the distribution argument. The strongest rebuttal is about who 'impractical' describes: Stuxnet cost a nation-state five years and multiple zero-days for one centrifuge model, so GPU-rental math doesn't bound state actors; and in the xz era, 'probably good enough' reads naive when compromising the weakest supply-chain link compromises everyone. The migration-forcing analogy lands hardest: PKI is moving to costlier postquantum crypto for the same reason — make it optional and nobody migrates until their walkie-talkie factory or compression library is suddenly critical. Chacon's pragmatic counter survives too: nobody is forced to run an unpatched Git 3.0, and carrying a SHA-1-default overlay is trivial —defaults are policy, and policy can be disagreed with locally.

    Pi Durable: crash-proof agents that resume where they died

    Alongside Pi 1.0, Earendil shipped Pi Durable, an experimental library for long-running agents that run anywhere JavaScript does and survive process death. Every step is a checkpointed task: reopen the same SQLite/JSONL storage and unfinished work resumes — aborted model calls resend, safe tool calls rerun, unsafe ones are reported interrupted, and requestIds make submissions exactly-once. Conversations fork without copying history, each with its own model, tools, and working directory; subagents are a few lines because a subagent is just another conversation.

    • The design
      • Every step a durable task; checkpoints before moving on
      • Resume after crash: resend, rerun-if-safe, or report interrupted
      • requestId exactly-once submissions; forks share history by pointer
    • The shape
      • ~15K lines total; memory/SQLite/JSONL backends, Cloudflare-ready
      • Library, not SDK — compose it, per Pi's minimalism
      • Extensions: prompt sections + tools, durable like everything else
    • HN take
      • Everyone's building this: LangChain, Vercel Eve, OpenAI, Anthropic
      • Open question: how do runner/VM states stay in sync after a crash?
      • Tree vs fork debate resolved: same function, flatter structure
    Source: earendil.com · Discuss: HN Discuss · 438 pts / 57 comments

    What HN commenters are sayingThe thread is builders comparing notes, because everyone is suddenly building this: Dagger-based 'dagger agent' replaying OpenTelemetry function recipes through crashes and OOMs, Lightspeed, LangChain Deep Agents, Vercel Eve, OpenAI's Agents API, Anthropic Managed Agents. The consensus on why now: durability makes unattended long runs, recovery, and monitoring tractable; separating harness from compute buys safety and scale; and multi-player steering gets easy. Pi Durable's distinction, noted appreciatively, is that it's a library you compose rather than a batteries-included SDK — true to Pi's philosophy, and an open bet on which shape wins. The sharpest unanswered question is state sync: checkpointing the agent's transcript is easy, but if the runner's browser was on page N and the new runner starts at page 0, who notices? The practitioner answer is human-like: make steps idempotent, clean up drafts, replay safely — workflow-engine discipline, not magic. A smaller design thread closes cleanly: Durable's forks-with-ancestry replace Pi's parented-entry tree because flattening the tree on every /tree was, in the author's words, exceptionally dumb.

    'Several vulnerabilities' in the Linux kernel: several hundred, actually

    Debian's DSA-6528-1 (Sep 29) patches the Linux kernel against a CVE list that runs to several hundred entries — the HN headline's 'several' doing heavy lifting. Context: since the kernel team became its own CVE authority, nearly any bugfix can get a CVE, because at the kernel's layer almost any bug might be exploitable. The advisory is one stable update's worth of that policy meeting an era of AI-assisted bug hunting.

      • Kernel policy: assign CVEs cautiously-broadly; triage is the reader's job
    • The backdrop
      • Post-Nov-2025 ('November Singularity'): AI-found advisories surging
      • One smaller project: 6 advisories/month → 22 last month
      • 'Number of CVEs' as a metric: 'useless,' per kernel docs
    • HN take
      • Zero-CVE deployment policies meet a 1,000-CVE release: good luck
      • Bug vs vulnerability: Therac-25 killed people with no adversary involved
      • Most CVEs irrelevant to most systems — but who has time to check?
    Source: lwn.net · Discuss: HN Discuss · 425 pts / 303 comments

    What HN commenters are sayingTwo threads braid together. The first is scale: a maintainer of a much smaller project reports jumping from six responsibly-reported advisories a month to 22 since what commenters are now calling the November Singularity — the late-2025 inflection where AI bug-hunting got good — and notes we now 'fight AI fire with fire,' hand-reviewing everything; whether that keeps up at kernel scale, where bugs scale with codebase size, is an open worry. The second is semantics: the kernel assigns CVEs to nearly any bugfix because any kernel bug is potentially a local DoS or privilege boundary failure, which makes raw CVE counts a useless security metric and zero-CVE deployment policies a business-halting fantasy when one release carries a thousand. The bug-versus-vulnerability distinction gets its best formulation via Therac-25: lethal, but no adversary, so not a vulnerability — yet no less urgent to patch. The pragmatic consensus is uncomfortable: most CVEs are irrelevant to most systems, vendors mostly prioritize correctly, and almost no admin team has the hours to verify that for four-digit CVE counts.

    RIP, vector database: turbopuffer kills its primary index

    turbopuffer is rebuilding its storage (v3) to demote the ANN vector index from primary key to 'just another' secondary index. The vector-primary layout — every document stored under its ANN address — causes storage amplification (multi-vector docs duplicate content), write amplification (SPFresh rebalancing drags whole documents and their inverted indexes along), and capped vectorization (100–200-document clusters vs the thousands-row blocks modern engines want). v3 passes 100% of CI; public benchmarks follow.

    • The problem
      • ANN-primary: documents keyed by cluster/local ID since v1 (SPANN→SPFresh)
      • Write amplification: one vector update moves hundreds of attributes
      • Block size stuck at 100–200 vs DuckDB's 2,048 / ClickHouse's ~65K
    • The fix
      • v3: don't key on the ANN address; ANN becomes a secondary index
      • Unlocks GROUP BY, aggregations, SQL-shaped queries at speed
      • 100% CI passing; perf grind now public, production rollout after parity
    • HN take
      • 'You went from a Postgres design to a MySQL one' — index→PK vs index→row
      • MySQL clustered-index virtues: undo logging, no vacuum; cached PK walk
      • 'Worse is better' — MySQL's stupidest-thing-that-works v1s, fixed in v2
    Source: turbopuffer.com · Discuss: HN Discuss · 354 pts / 100 comments

    What HN commenters are sayingHN reads turbopuffer v3 as a database-history rerun: keying secondary indexes by primary key instead of by physical row address is the MySQL/InnoDB move, versus Postgres's direct TID pointers. The thread argues both sides properly — Postgres does less work per lookup, but the MySQL layout enables undo logging (no vacuum, Postgres's most painful ritual), and since the primary-key index is mostly cached, the extra B-tree walk is small next to a disk read. 'Worse is better' gets invoked with affection: MySQL's history of shipping the stupidest thing that works, then fixing it (statement-based binlog until UUIDs broke it, file offsets until GTIDs), is presented as a feature. A meta-thread accuses several comments of being LLM output quoting LLM output — 'hopefully the original authors end up having the LLM respond back' — and gets pushback that HN was always founders pitching each other; the robots just type faster now. On the post itself: respect for publishing the perf grind from day zero, and for an architecture that already serves 100B+-vector indexes admitting its founding layout became the ceiling.

    DeepSeek Harness goes public: everything is a plugin

    DeepSeek Harness (dsh) launched in public preview worldwide, open source, built on the Cordis 'everything is a plugin' architecture. It runs as an Electron desktop app (macOS/Windows) wrapping the full dsh web UI, or headless via `npx @deepseek-ai/dsh web`. Plugins hot-swap capabilities without restart — activate/deactivate functions over a shared context, declared provided/required services, lazy activation — and can be created through chat in Creator mode. Everyday work, coding, research, and scheduled background tasks are the launch surface.

    • What shipped
      • DeepSeek Harness public preview, open source, worldwide
      • Desktop (Electron) + web UI: `npx @deepseek-ai/dsh web`
      • Cordis architecture: every capability a hot-swappable plugin
    • The model
      • Plugins declare services; dependencies checked before activation
      • Creator mode: build plugins through chat; scheduled-tasks plugin
      • Note: desktop build enables telemetry by default (web: feedback only)
    • HN take
      • 'All the AI harnesses are Electron crap' — native would be trivial?
      • 'The Emacs of harnesses' claim meets 'fairly standard plugin interface'
      • Plugin trust problem: third-party malware vs curated feature sets
    Source: deepseek.com · Discuss: HN Discuss · 318 pts / 161 comments

    What HN commenters are sayingThe thread splits three ways. The architecture discussion: Cordis excites people — capabilities that enable and disable without restart, with dependency satisfaction checked before activation, reads to one commenter as a potential 'Emacs of harnesses,' especially for long-running agents; a reader of the paper demurs that in plain engineering terms it's a fairly standard plugin interface with disciplined lifecycle rules, which prompts the day's best exchange — Emacs users insisting agent-shell inside Emacs is already the harness to beat ('agents have become pretty good at writing elisp'), skeptics asking what Emacs actually buys you. The Electron complaint recurs with feeling: every harness ships an Electron shell around a web app, and if the AI can write the harness, why can't it write native frontends — Codex's desktop is Electron too, someone confirms. The practical flags: the desktop build enables telemetry by default where the web build doesn't, and the plugin-skeptic position — third-party plugins as malware and abandonment risk versus a curated, polished core — with VS Code's ecosystem held up as the world everyone now lives in, like it or not.
