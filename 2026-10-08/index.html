    Margaret Hamilton, who led Apollo flight software, dies at 90

    MIT reports Margaret Hamilton died Sep 30 at 90. She led the team that built Apollo's onboard flight software at MIT's Instrumentation Lab, pushed for software to be treated as engineering in its own right, and later founded two software companies. Her team's priority-driven design is the reason the Apollo 11 landing could proceed through the 1202 overload alarm.

    • The work
      • First programmer hired for Apollo at MIT; led onboard flight software
      • Team grew to 400+ people by the crewed missions
      • Defensive, priority-driven software: shed low-priority tasks under load
    • The record
      • 130+ publications; Presidential Medal of Freedom in 2016
      • NASA Exceptional Space Act Award in 2003
      • Apollo code published on GitHub in 2015; Lego figure in 2017
    • Why it matters
      • She made reliability and error handling a design discipline, not an afterthought
      • The P01 / Apollo 8 incident is still the textbook case for designing for operator error
      • A career that started when 'software engineering' was treated as a joke
    Source: news.mit.edu · Discuss: HN Discuss · 1826 pts / 200 comments

    What HN commenters are sayingA memorial thread, and a long one by HN standards for an obituary. Commenters trade first encounters with the famous photo of Hamilton beside the stack of Apollo code, link the Computer History Museum oral history, and argue the lineage point: that her insistence on rigour predates and enables later formal methodologies rather than following them. Several call it a black-bar day. There is no real disagreement here, just an unusually specific shared debt: priority scheduling, defensive programming, and taking software seriously as engineering all trace back to that team.

    Show HN: Bigwords.page — the URL is the sign, no backend, nothing stored

    Bigwords.page turns any screen into a full-screen sign, timer, or message, configured entirely in the URL fragment — which browsers never send to a server, so there is no account, no app, and no stored message. Text auto-fits any screen, supports Markdown, rotating slides split by ||, countdowns via &until= or &timer=, and QR codes and images generated locally in the browser. The author built it to put a message on a remotely managed tablet he could not physically reach.

    • How it works
      • Message lives in the URL fragment; never sent to a server
      • All parameters documented, so links can be generated by any tool
      • Open source; every use-case card on the homepage is itself a working link
    • Features
      • Auto-fit text from phone to stadium board, any browser
      • Markdown, slides on a timer, countdowns and timers
      • QR codes for links, Wi-Fi, calls, texts, email — generated client-side
    • Why it matters
      • A complete product with zero backend to run, secure, or pay for
      • Useful exactly where apps are not: arrivals boards, front desks, conference screens

    Tao on 'Math 2.0': progress will need valuing more than solved problems

    Terence Tao's post, linked via Mastodon, argues that a coming 'Math 2.0' will need to value mathematical progress more holistically — not only headline solutions to named open problems, but understanding, exposition, and the work of connecting results. It lands the same week as OpenAI's large AI maths release, which makes the question concrete: if machines produce proofs faster than humans can absorb them, what should the field reward?

    • The argument
      • Value progress holistically, not just by problems solved
      • Understanding and explanation are part of the progress, not overhead after it
      • Posted as the AI maths results (stories 2 and 8) dominate discussion
    • The pressure underneath
      • Hiring and prestige still track top-tier papers and named results
      • AI shifts scarce effort from solving toward verifying and explaining
      • Workshops and digestion work need status if they are to get done
    • Why it matters
      • This is the incentive-design question behind the Mathocalypse argument
      • If only solutions count, nobody is rewarded for making solutions usable
      • Tao is a member of the advisory circle around the OpenAI release
    Source: mathstodon.xyz · Discuss: HN Discuss · 429 pts / 412 comments

    What HN commenters are sayingThe thread takes the incentive point seriously and tests it against academic reality: one commenter doubts any hiring committee will stop counting top-tier papers, and sketches departments instead spending grant money on AI access for fewer students. Another line argues the understanding gap is temporary — that if models keep improving, they will also explain their proofs step by step, dissolving the digestion problem Tao is organising around. The sharpest short answer to how you formalise 'interesting' is a single word: taste. Which is, in effect, Tao's point stated from the other side.

    The Mathocalypse: Aaronson on 372 AI results, including the Unique Games Conjecture

    Scott Aaronson's long post works through OpenAI's maths release from inside theoretical computer science: among the hundreds of results he lists a claimed proof of the Unique Games Conjecture — a problem his wife Dana Moshkovitz has worked on for her whole career — plus L=BPL, a sub-n log n Fourier/integer-multiplication result, and progress touching several Millennium-adjacent problems. He is clear on the epistemic state: some results carry Lean certificates, and no human yet understands most of the proofs.

    • Scale, per Aaronson
      • 372 results released on the advisory group's recommendation
      • Model tried ~8,000 problems; roughly 5% solved per attempt, per his sources
      • Average ~3 hours of GPT-Pro-level compute per solved problem
    • Named in the post
      • Unique Games Conjecture, with a Lean certificate
      • L=BPL derandomisation result
      • Unitary Synthesis Problem solved positively, against most expectations
    • The open argument
      • OpenAI model: publish raw, let humans race to digest
      • Anthropic model, in a parallel case: let the human researchers write it up first
      • Cryptography conspicuous by its absence from the list, per his update
    Source: scottaaronson.blog · Discuss: HN Discuss · 298 pts / 312 comments

    What HN commenters are sayingThe thread argues about value, not existence. The hardest line says statistically guided brute force that produces no human understanding adds nothing and may harm the field. The counter-line, quoting a professor in-thread, is that PhD problems solvable in 15 minutes by public models turn the defence into a test of understanding rather than of production — which may be the healthier test. A third complaint is aesthetic: several breakthrough bounds beat the old mark by a hair in the exponent, which reads as the machine doing the minimum to win. The teleport-to-the-summit metaphor from the post is the image commenters keep reusing, approvingly and critically at once.

    Docker Agent: build and run agent teams from YAML, as a Docker CLI plugin

    Docker Agent is Docker's open-source (Apache-2.0) agent builder and runtime: define agents declaratively in YAML with instructions and toolsets — built-in tools plus any MCP server — and run them via the docker agent CLI plugin, pre-installed in Docker Desktop 4.63+. It is provider-agnostic (OpenAI, Anthropic, Gemini, Bedrock, Mistral, xAI, or local Docker Model Runner), supports multi-agent delegation, RAG, and packaging agents as OCI images to share through any registry.

    • The tool
      • docker agent run agent.yaml; also runs agents straight from OCI registries
      • YAML config: model, instructions, toolsets; no code required
      • Built-in think, todo, and memory tools; RAG with BM25/embeddings/hybrid
    • The repo
      • Go project, Apache-2.0; ~4,100 stars at fetch time
      • 262 releases; Docker itself uses it to build itself, per the README
      • Sandbox documentation lives under the docs site, not the repo front page
    • Why it matters
      • Distribution is the pitch: agents as OCI artifacts, Docker's home turf
      • Provider-agnostic runtimes are commoditising fast — differentiation moves to packaging and trust
      • Another major-vendor harness entering a crowded field
    Source: github.com · Discuss: HN Discuss · 269 pts / 124 comments

    What HN commenters are sayingThe thread is sceptical in a specific way: agent harnesses are compared to JavaScript frameworks in their proliferation era — every vendor has one, and coolness is not a moat. The pointed questions are what this has to do with Docker beyond branding, where the sandboxing story is (one commenter supplies the docs link the repo page lacks), and why you would choose it over existing sandboxed agent platforms with network-level isolation. Defenders are thin on the ground in the top comments; the burden of proof, HN has decided, sits with the harness number fifty.
